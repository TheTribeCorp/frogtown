---
name: SWAMP encryption model
description: Security constraints and user-facing limitations of SWAMP's recipient-only message encryption.
---

SWAMP wallet authentication does not provide an encryption key. Keep message secrets client-side, never restore server-side message decryption, and do not silently replace a registered public key because old messages depend on the matching local private key. Before persisting a message, validate its envelope on the server; direct-message envelopes must cover every member, while group envelopes must exactly cover all members with registered encryption keys. Group members without keys are deliberately omitted and warned that they cannot receive those messages; no plaintext fallback is allowed. Group history is automatically shared after a join: an already-present member's active device decrypts only messages it can read and re-encrypts each one exclusively for the newcomer. The server stores only that recipient's ciphertext, and history backfill waits until an eligible existing member opens the room. Device recovery uses a passphrase-encrypted file; verify the wallet and existing public key before restoring, and never send the passphrase or private key to the server. Keys created before encrypted backup support are non-exportable, so losing their original browser data without an existing backup means losing access to that history. If a user explicitly starts fresh without a backup, retain their group memberships, replace only their wallet's encryption key, hide messages and shared history from before their reset cutoff for that wallet, and preserve source messages for other participants. The server's public-key directory can be substituted by a malicious server; users need to compare the conversation safety code through a separate trusted channel. This custom protocol has not received an independent security audit.

**Why:** A wallet address proves the logged-in identity but cannot derive a shared encryption secret without exposing the wallet's signing key; an unauthenticated public-key directory creates a key-substitution risk. A group sender could also include a non-member's public key in a ciphertext envelope; that wallet could later join and retrieve older ciphertext unless the server checks envelope recipients against membership and registered keys at send time. The user chose automatic history sharing and later explicitly approved sending to key-ready group members with a visible warning for members without keys; plaintext must still never pass through the server. The user also chose that a no-backup fresh start keeps groups but begins with new chat history.

**How to apply:** Preserve the client-only trust boundary in future messaging changes, validate each send's recipient set against server-side conversation membership and key readiness, keep recovery and key-verification warnings visible, never overwrite a mismatched local key silently, and review protocol changes before claiming production-grade secure messaging. For group history, enforce that the sharer belonged to the room when the source message was sent, the recipient joined later, and each stored share targets only that recipient. A fresh-start reset must enforce its cutoff in message reads, unread counts, previews, read receipts, and history sharing, without deleting global source messages or removing group membership. Messages sent before an existing member registers a key are not automatically recoverable under the current history-sharing eligibility rule.
